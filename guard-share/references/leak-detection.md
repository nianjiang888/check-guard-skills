# 泄露检测方法与量化模型（guard-share 引擎说明）

## 一、检测方式：纯静态正则 + 复合规则

guard-share 引擎不依赖网络、不调用第三方服务，纯靠本地正则对文本文件做内容扫描。两种匹配模式：

### 1. 逐命中模式（逐条内容规则）

对 PII、密钥、商业敏感、内部文档这类「内容本身即风险」的规则，引擎在文件里逐处匹配：

- `SHARE-PII-ID`：`\b\d{17}[\dxX]\b` 识别 18 位身份证号字面。
- `SHARE-PII-PHONE`：`\b1[3-9]\d{9}\b` 识别 11 位手机号。
- `SHARE-SECRET-APIKEY`：识别 `api_key/secret/token/password = "值"` 这类明文赋值。
- `SHARE-SECRET-PRIVKEY`：识别 `-----BEGIN ... PRIVATE KEY-----` 私钥块。
- `SHARE-SENSITIVE-PRICE`：识别报价/底价/合同金额等商业敏感字面。
- 其余规则同理。

每处命中带上下文窗口做白名单过滤（`your-`/`dummy`/`test`/`sample`/`示例`/`虚构`/`仅为演示` 等语境放过），避免把练习代码误判为真实泄露。

### 2. 文件级复合模式（分类/溯源缺失）

对「有敏感内容但无处置标记」这类规则，引擎用 `req_regex`（必须出现敏感内容）+ `absent_patterns`（不能出现处置标记）做文件级单次判定：

- `SHARE-CLASSIFY-MISSING`：文件含敏感关键词，却无 `密级/机密/秘密/内部/公开/confidential/classified` 等任一标签 → 命中。
- `SHARE-WATERMARK-MISSING`：文件含敏感关键词，却无 `溯源/水印/watermark/canary/分类标签/蜜标` 等任一标记 → 命中。

复合规则避免「内容有了、标签也顺手写了」被误报，只在「内容有、标记无」时才提示。

## 二、量化模型：外发泄露指数

命中按严重度累加权重，封顶 100：

| 严重度 | 权重 |
|--------|------|
| 极端 | 100 |
| 高 | 40 |
| 中 | 12 |
| 低 | 3 |

**判定取严重度优先级链，不取平均**：只要有一条极端即判极端，有一条高且无极端即判高，如此类推。这样不会被一堆低危稀释掉真正高危的那一条。

## 三、可溯源性维度（本包原创量化点）

每条内容泄露命中（PII / 密钥 / 商业敏感 / 内部文档层）的「可溯源 / 不可溯源」不是写死的，而是由**同文件是否带溯源标记**动态判定：

- 文件含敏感内容 **且** 同文件带密级/水印/canary/分类标签等标记 → 该命中记为 **可溯源**（泄露后还能追到副本与经手人）。
- 文件含敏感内容 **但** 无上述标记 → 该命中记为 **不可溯源**（泄露后追不回来）。

复合规则（分类缺失、溯源缺失）只在标记缺失时触发，本身即属 **不可溯源**。

这样做的好处：报告里 `可溯源 X 处 / 不可溯源 Y 处` 是引擎实算出来的，不是套话——它直接告诉发送人「这份文件里有多少敏感内容是裸奔的、追不回来的」。

## 四、安全控制价值量化

把「没发生的泄露」折算成可感知数字：按判定等级估算避免的溯源补救与泄露处置工时——极端 8h / 高 4h / 中 1h / 低 0h。这是把合规与处置成本语言化，让「加个水印、定个密级」的投入有依据。

## 五、诚实边界（必须写明）

1. 只在静态内容层面检测，不实际拦发送、不修改文件。
2. 对文件最终是否真的发出、发给谁、通过什么渠道无感知。
3. 正则启发式，漏报与误报并存：变量改名、间接引用会漏；个别普通字段会被误报。规则仅作提示。
4. 可溯源性不是「已溯源」保证，只提示「这些泄露是否带标记可追」，是否真能追到须结合标记部署与人工确认。
5. 不评估数据真实敏感度，只量化静态可见风险。
