# check-links 常见问题（FAQ）

| 场景 | 话术 |
|---|---|
| 「我的链接本地都能点开，还要检查吗？」 | 本地能点开不等于发布能点开。相对路径一换仓库结构、锚点一改名就断了，check-links 在发布前替你扫一遍这类低垂的坑。 |
| 「它会不会误报我的外链？」 | 不会。外链（带 `://` 的真实网址）和裸域名不做文件存在性判定，只有本地相对引用、页内锚点、占位/空链/语法问题才会被标记。 |
| 「import 的文件没了，为什么是极端？」 | 因为代码/配置的 import/require/include 缺失会直接导致构建失败、产物不可发布，属于「发布即崩」的坑，故定极端级并建议阻断。 |
| 「它会不会联网探活外链？」 | 不会。check-links 只做静态可解析性判定，不发起任何网络请求，因此不受网络/墙影响、可重跑、可进 CI。 |
| 「页内锚点失效为什么是中而不是高？」 | 它影响导航体验但通常不导致构建失败，故定中级；极端留给 import 缺失这类「构建即崩」的坑。 |
| 「和 guard-network 有什么区别？」 | guard-network 查的是外联/数据外泄通道（安全视角），check-links 查的是引用能不能解析到（死链 lint 视角）。两者入口不同、互补不替代。 |
| 「扫描会扫到测试文件吗？」 | 文件名含 test_/example/sample 或内容带明确测试标记（fixture/测试专用示例）会被跳过；真实文档即使含 example 等词也不会被跳过，以免漏报真实死链。 |
| 「支持哪些引用写法？」 | Markdown 链接/图片、HTML 的 src/href、YAML 的 include/path/url、Python/JS 的 import/require/!include 都识别，按通用模式匹配，不挑框架。 |
| 「扫描太慢/太多文件怎么办？」 | 直接指到具体文档目录或文件即可，不必扫整个仓库。 |
| 「升级后规则变了，旧报告还作数吗？」 | 以当前版本 rules.json 为准。升级时本包会保留旧版说明，建议按新规则重跑一次。 |
