# 死链 / 坏引用检测的方法论依据

死链是最隐蔽也最常见的发布缺陷之一：本地能跑、仓库能过，一发布读者点击就 404，或构建流水线在 CI 里直接挂掉。check-links 的判定逻辑建立在以下原则上：

## 1. 引用必须可解析（Resolvability）

任何引用（文件、锚点、资源）在加载时都应能被解析到真实目标。无法解析的引用应在构建期/发布前暴露，而不是发布后失效。

check-links 据此把「import/require/include 缺失」列为极端级——因为它是构建级错误，缺失即构建失败、产物不可发布；把「相对文件引用缺失」列为高级——它通常让文档/页面出现破图或断链。

## 2. 链接卫生（Link Hygiene / 零占位）

对外发布的文档不应包含：
- 示例/占位域名（example.com、your-domain、localhost）—— 对读者全部等于死链；
- 空链接（`[]()`、空 `href`）—— 点击无反应；
- 语法非法链接（URL 内含空格、www 缺少协议头）—— 解析器会丢弃或错乱。

check-links 的 placeholder / empty / malformed 三条规则即据此。

## 3. 锚点唯一性

同一文档内多个相同标题会生成相同锚点（`#intro` 出现两次），点击跳转必然指向第一个，造成「看起来有锚点其实跳错」。静态检查可提前发现重复锚点。

## 4. 为什么是静态检查而非实时探活

实时 HTTP 探活慢、受网络与区域限制、不可重跑、难以稳定进入 CI，且对「本地相对文件引用」「页内锚点」这类根本不需要联网的死链毫无必要。静态检查在部署前就能跑、可重跑、可留证据，专门拦住「文件/锚点/语法」这类不需联网就能判定的死链。它不替代运行时的链接监控，而是把「发布前最后一次引用复核」标准化。
