# check-tender-rejection 是什么

check-tender-rejection 是标书提交前的「废标风险基线护栏」。不是法务合规审查（那是专业招标顾问和律师的活），也不是全量标书审计，而是更日常的「废标 lint」——把标书推走之前，先替你把最常见、最容易被看漏的废标雷区扫一遍：资质证书缺失或过期、签章漏在关键页、工期起止写反、报价超出限价、技术条款偏离招标要求、占位符忘了替换。

标书"看起来没问题"往往只是没被认真扫过。这些缺陷不会让文件报错，却会在资格性审查那一关直接出局——保证金白押、全组一个月白干、这个标的彻底错过。check-tender-rejection 要做的，是把"提交前最后过一遍"变成可重跑、可量化、留证据的静态检查。

## 能做什么

31 条规则按五层组织，对应评审的三道闸口：

| 层 | 查什么 | 说明 |
|---|---|---|
| qualification 资格 | 营业执照、资质证书、安全生产许可证、授权委托书、投标保证金、业绩、人员证书、无行贿承诺 | 缺一项直接出局，多数补不回来 |
| formality 形式 | 签章完整性、投标有效期、报价是否超限价、投标函、条款偏离 | 可补救，但要赶在截止时间前 |
| consistency 一致性 | 金额大小写、工期逻辑、证书有效期、人员与证书匹配、页码连续 | 前后矛盾会被判非实质性响应 |
| format 格式 | 字体字号页边距、占位符残留、公司名称写错、联系方式 | 部分招标文件明确列为废标条款 |
| technical 技术 | 施工方案章节完整性、技术参数逐条响应 | 关键参数不响应即废 |

算「废标风险指数(0-100)」与「预计避免损失」，出可修正性报告，退出码 0/1/2/3/4。

## 边界（重要）

- 只读纯文本（.md / .txt）。Word、PDF 需先转文本，扫描件需先做 OCR，否则什么都扫不出来。
- **读不到招标文件**，因此不知道本次招标的具体限价、资质等级要求、有效期天数。凡涉及具体数字的比对，报告只提示"需人工核"，不代替你判断。
- 规则是工程、货物、服务、政府采购四类的通用最大公约数，未按行业分化。判不了量身定制的隐形排他条款。
- 不修改标书、不拦截提交、不承诺 100% 准确。命中不等于必然废标，未命中也不保证中标——这是提交前的体检，不是中标保险。

## 怎么用

```
python scripts/check.py scan <标书文件或目录> [报告输出路径]
python scripts/check.py rules                  列出全部规则
python scripts/check.py ledger <标书目录>       输出 JSON，供脚本消费
python scripts/check.py version
python scripts/smoke_test.py                    四档样例隔离实跑自检
```

扫描结束输出判定（通过 / 低 / 中 / 高 / 极端）、废标风险指数、可修正与不可修正数量、发现项数、预计避免损失，报告末尾附机器可读的 `REJECTION_RESULT {...}` 判定块。

退出码：0 干净，1 有命中，2 输入输出错误，3 命令写错，4 命中极端项（必废标，如报价超限）。

## 免费版与付费版

免费版跑 10 条基础规则（资质证照、签章、工期三块），付费版跑全量 31 条并附逐条修改建议。当前分发版本为免费版，frontmatter 中保留了 A2M 计费三件套的配置位置，改收费时启用即可，无需改动规则与引擎。

## 与其他 check 成员的关系

- check-accessibility：校验「可访问性基线」。
- check-links：校验「引用关系」是否断裂。
- check-spelling：校验「文字与排版」是否干净。
- check-secret-scan：校验「明文密钥/凭证」是否泄露。
- check-schema：校验「数据 schema 字段约束」是否缺失。
- check-docs：校验「文档与代码一致性」。
- check-lockfile：校验「依赖锁定完整性」。
- check-tender-rejection（本包）：校验「标书废标雷区」。

check-tender-rejection 专注「标书提交前的底线硬伤」这一层。
