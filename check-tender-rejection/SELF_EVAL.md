# SELF_EVAL：TRACE 5D 自评

版本 v1.0.0　评估时间 2026-09-06　评估对象：check-tender-rejection

打分口径：5 分制，取整数与半档。任一维低于 5.0 必须写明具体问题，不许用"待优化"这类空话糊过去。

---

## T — Task 契约　4.5 / 5

**做对的**：四条命令（scan / rules / ledger / version）输入输出明确，退出码 0/1/2/3/4 各有语义，报告末尾的判定块字段固定为 verdict、exposure_index、fixable、unfixable、findings、avoid_loss、scan_time 七项。冒烟测试对这七项做了存在性断言，并额外校验 fixable + unfixable = findings 这个自洽关系。

**扣 0.5 的原因**：文件类型契约过窄。规则里 ext 只写了 .md 和 .txt，Word 和 PDF 必须先用外部工具转成文本才能扫。对真实用户来说，标书 99% 是 .docx，这一步摩擦足以劝退一半人。这是契约设计上的缺口，不是实现 bug。

**下一步**：加一个 `--from-docx` 前置转换，或在 SKILL.md 里把转换命令写成可直接复制的一行。

---

## R — Robustness 鲁棒性　4.0 / 5

**做对的**：规则文件读不了会走 _die 退出码 2；日期解析包了 try/except，解析失败就跳过不崩；样例文件用的是独立临时目录隔离，互不污染；白名单跳过 fixture 类文件；金额和日期规则带 min_count 阈值，不会在只有一两处正常表述时乱报。

**扣 1.0 的原因**：两条实打实的脆弱点。

1. rules.json 里的 pattern 字段没有做任何正则合法性校验。用户自己加规则时写坏一个正则，引擎会在 re.search 处直接抛异常崩掉，而不是报"第 N 条规则正则非法"。规则外置的意义就是让人改，改错了却给个崩溃，说不过去。
2. 没有文件大小上限。丢一个几百 MB 的文本进去会整个读进内存，虽然这次的用场景（标书）不太可能，但作为 check 系列的一员，其他包有这个兜底，本包没有，属于退步。

**下一步**：加载规则时逐条 re.compile 校验，失败则打印规则 id 并跳过；读取文件加 8 MB 上限，超限跳过并记一行警告。

## A — Applicability 适用性　4.0 / 5

**做对的**：31 条规则按资格、形式、一致性、格式、技术五层组织，对应评审的三道闸口。`resources/check-tender-rejection-domains.json` 里明确了适用边界：工程、货物、服务、政府采购四类。四档样例（clean / mid / high / combo）覆盖了从零命中到必废标项的完整区间。

**扣 1.0 的原因**：规则是"通用最大公约数"，没有行业分化。工程类标书必查安全生产许可证和建造师证，货物类看重的是产品授权和检测报告，服务类看的是人员配置和服务方案。现在用同一套规则套所有类型，结果是对工程类偏准，对货物和服务类会漏掉不少专属雷区，同时报一些不那么相关的项。

另一条：本包读不到招标文件，所以所有涉及具体数字的比对（限价多少、资质几级、有效期几天）都只能提示"需人工核"。这个限制写进了边界章节，但它确实是适用性上的硬伤——最有价值的检查恰恰是这些。

**下一步**：按 domains.json 里的四类做规则分组，scan 时支持 `--domain=engineering` 之类的参数只跑相关规则集。

---

## C — Clarity 清晰度　4.5 / 5

**做对的**：报告主体是一张七列的表，每行给出严重度、规则、层、文件、说明、能否补救、怎么改，投标人拿到就知道下一步做什么。方法论文档解释了五层怎么来的、三种判定机制各自的分寸、量化口径的换算依据。FAQ 按"场景 / 看到的结果 / 疑问 / 退出码"四类组织，不用读完全文就能查到。

**扣 0.5 的原因**：报告里的"预计避免损失 ¥1,450,000"是个量级估算，依据是严重度基数累加，不是任何精算模型。方法论和 FAQ 都写清楚了，但**报告正文本身没有标注**。用户截图发出去的往往就是这一行，脱离上下文后极易被当成精算结果。这是清晰度问题，不是准确性问题。

**下一步**：报告里改成"预计避免损失（量级估算）"，或在表头加一行脚注。

## E — Evidence 实物证据　5.0 / 5

这一维给满分，因为证据链是完整的、可复现的：

1. 四份样例报告全部由引擎实跑产出，`python scripts/smoke_test.py` 可一键复现，结果 4/4 PASS。判定、暴露指数、发现项数、预计损失、退出码五项断言全过。
2. clean 样例做到 0 命中 0 误报，这是压误报能力最有力的证据——不是"没扫出问题"，是"扫了 31 条规则确实没问题"。
3. high 样例命中极端档并正确返回退出码 4，证明一票否决项不会被一堆低危项稀释。
4. 调试过程中的三个真实缺陷都有迹可循：missing_any 的同义词 OR 语义写反导致大面积误报、工期倒挂只判断字段存在而不比日期、样例文件命名撞上引擎白名单被整体跳过。三个都修了，且修法写进了方法论的"三种判定机制与各自的分寸"一节。
5. rules.json 通过 JSON 合法性校验，严重度取值全部落在引擎字典覆盖范围内。
