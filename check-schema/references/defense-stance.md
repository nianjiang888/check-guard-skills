# 防御立场与诚实声明（check-schema）

本文件说明 check-schema 在「帮你拦住 schema 约束缺失」这件事上的立场与边界。它不是类型推导引擎，而是一道可重跑、可量化、留证据的静态防线。

## 一、立场：拦得住的才拦，不假装全能

- 只做不需要语义理解的确定性模式：缺 required、缺 type、邮箱未标 format、有限值未标 enum、字段无 description。这些恰恰是「人容易看漏、工具一眼揪出」的低垂约束缺口。
- 不做全量类型推导（发现「字段类型逻辑矛盾」「跨字段依赖」），也不做运行时采样比对。那超出了静态快检的能力，强行做只会制造误报，反而让人不再信任工具。

## 二、诚实边界

- 不承诺 100% 准确：缺 required/type 几乎零误报，但邮箱/有限值字段在命名巧合时会误报；报告里每条都标注命中类型（如「出现 email 字段却没标 format」），由人最终裁决。
- 不修改文件：只产出报告与机器可读判定块，是否修复、怎么修复由使用者决定。不替你改 schema，避免「自动修正」引入新问题。
- 不拦截部署：返回退出码供 CI 消费，但是否阻断由流水线策略决定；本包对极端级约束缺失返回退出码 4（极端级，建议阻断）。

## 三、与同类工具的关系

- 与 guard-schema 互补：guard-schema 做深度防护（类型推导 + 依赖校验 + 历史扫描），check-schema 做快检版（模式命中即报）。两者入口不同、互不替代。
- 与专业 schema 校验器（jsonschema/pydantic 等）错位：那些做运行时深度校验，本包做轻量、可进 CI 的确定性检查，二者可叠加使用。

## 四、可修正性量化的意义

每条发现都带「可修正 / 不可修正」标记（缺约束一律「可修正——补上对应字段」），并汇总成「验证暴露指数」与「预计避免返工工时」。这让 schema 风险从「感觉不规范」变成可比较、可追踪的数字，也方便在多个文件 / 多个包之间排优先级。
