# 防御立场：看清后果再决定，不硬禁止

## 一、为什么不是「硬禁止」

所有 guard 系列共享同一立场：护栏的价值是「让人看清后果」，而不是「替人把门关死」。

记忆/上下文污染场景里，硬禁止会带来更坏的结局：

- 开发者为了「能跑」会绕过护栏（`--no-verify`、裸写 `memory.add`、把记忆移出检测目录）。
- 绕过后的代码反而**完全无防护**，污染照进不误。
- 安全工具的信誉在一次次「误报/挡活」里耗尽，团队最终弃用。

> 这与 guard-delete（破坏性操作）、guard-cost（付费调用）一致：本系列不实际拦截任何请求，只给出判定、暴露指数、价值量化与实物报告，决策权在人。

## 二、用「三重降误报」守住误报红线

误报会杀死产品，本引擎用三道手段压制：

1. **确实写了记忆才提示**：`MEM-*` 规则要求文件真正出现记忆写入调用（`req_memory`），不是在讨论记忆就报。
2. **确实不可信才升格**：`MEM-WRITE-UNTRUSTED` 要求文件同时存在不可信来源信号（`req_untrusted`）；`MEM-RAG-UNTRUSTED` 同理。空谈不误报。
3. **强制指令短语检测**：投毒类规则锚定「记住…忽略/你现在是…」这类强信号，普通注释里的「忽略」不会轻易命中（限定在记忆动词 120 字窗口内）。

## 三、诚实边界（必须写明）

- 不实际拦截任何请求，不感知运行时动态写入频次。
- 不承诺 100% 拦住——只是多层防御中的工具层（与 OWASP 防御纵深一致）。
- 污染后果取决于下游如何使用记忆，本工具只量化**静态可见**风险。
- 溯源/隔离/信任分级阈值仅为参考，真实以团队规范为准。

## 四、和系列其他成员的边界

| 成员 | 管什么 | 本成员 |
|------|--------|--------|
| guard-prompt | 单次输入里的注入 | 跨会话持久化的注入（记忆） |
| guard-secret | 密钥字段泄露 | 密钥被写进记忆（MEM-LEAK-SECRET） |
| guard-memory | 记忆读写 + 上下文拼接的污染 | —— |

guard-memory 站位是「长期状态与上下文的污染防护」，与 guard-prompt 是同一威胁的不同生命周期阶段。
