# 防御立场：看清后果再决定，不硬禁止

## 一、为什么不是「硬禁止」

所有 guard 系列共享同一立场：护栏的价值是「让人看清后果」，而不是「替人把门关死」。

高危命令场景里，硬禁止会带来更坏的结局：

- 运维确实需要 `rm -rf`、`dd`、`mkfs`，封杀它们等于封杀正当工具。
- 开发者为了「能跑」会绕过护栏（`--no-verify`、裸 root、把命令藏进检测死角）。
- 绕过后的脚本反而**完全无防护**，误操作照常发生。
- 安全工具信誉在一次次「误报/挡活」里耗尽，团队最终弃用。

> 这与 guard-delete / guard-cost / guard-memory 一致：本系列不实际拦截任何命令，只给判定、暴露指数、可回滚性与价值量化，决策权在人。

## 二、用「边界收敛」守住误报红线

误报会杀死产品。本引擎对危险命令本体做了边界收敛，避免「看到 rm 就报」：

- `CMD-RM-RF` 只匹配 `rm -rf` / `rm -fr` / `rm -Rf`，**不匹配**普通 `rm file`（那是有意删除）。
- `CMD-CHMOD-777` 要求数字权限恰好 `777`，不把 `755`/`644` 误判。
- `CMD-PIPE-SH` 要求「网络下载**直输 shell**」这一高危组合，不把普通 `curl` 下载误报。
- 安全变体（`--dry-run` / `rm -n`）识别为鼓励做法，而非命中。

## 三、诚实边界（必须写明）

- 不实际拦截任何命令，不感知运行时真实执行情况。
- 不承诺 100% 拦住——只是多层防御中的工具层。
- 危险后果取决于命令是否真被执行，本工具只量化**静态可见**风险。
- 阈值/匹配仅为参考，真实以团队规范与备份策略为准。

## 四、和系列其他成员的边界

| 成员 | 管什么 | 本成员 |
|------|--------|--------|
| guard-delete | 源码里的破坏性操作构造 | 命令/参数执行层的高危命令 |
| guard-secret | 密钥字段泄露 | curl|sh 把密钥脚本拉来执行（CMD-PIPE-SH 侧面相关） |
| guard-command | 高危命令与危险参数 | —— |

guard-command 站位是「命令执行前的风险可见化」，与 guard-delete 是同一威胁的不同切面。
