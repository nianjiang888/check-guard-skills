# 危险命令的爆炸半径：为何护栏在「执行前」

## 一、爆炸半径（SRE 实践）

执行任何命令前先想一个问题：**最坏情况下影响多大？**

| 命令 | 爆炸半径 | 可否回滚 |
|------|----------|----------|
| `rm -rf /` | 整台机器文件系统 | 不可（除非有备份） |
| `dd of=/dev/sda` | 整块磁盘数据 | 不可 |
| `mkfs /dev/sda` | 整块磁盘文件系统 | 不可 |
| `> /dev/sda` | 整块磁盘被覆盖 | 不可 |
| `:(){ :|:& };:` | 整机可用性（进程打满） | 不可 |
| `chmod 777 /var/www` | 该目录被任意篡改 | 可（改回权限） |
| `sudo su` | 之后所有操作在 root 下 | 可（退出 shell） |
| `curl x | sh` | 远端脚本随意执行 | 可（若未跑） |
| `git reset --hard` | 本地提交历史丢失 | 可（有 remote/reflog） |

不可回滚的命令，护栏必须是**执行前的确认与干跑**，而不是执行后的救火。

> 引用：Google SRE Book, Change Management / Blast Radius 实践。

## 二、为什么「硬禁止」会失败

对所有危险命令一律封杀，现实里行不通：

- 运维确实需要 `rm -rf`、`dd`、`mkfs`——它们是正当工具。
- 一刀切封杀只会逼出绕过：`--no-verify`、裸 root、把命令写进检测不到的角落。
- 绕过后的代码**完全无防护**，事故照样发生。

所以本引擎的立场是「看清后果再决定」：给出判定、暴露指数、可回滚性、价值量化，由人拍板。

## 三、与系列其他成员的边界

| 成员 | 管什么 | 本成员 |
|------|--------|--------|
| guard-delete | 代码里的破坏性操作构造（rm 出现在源码/SQL DROP） | 命令/参数层的高危执行（shell 命令、CLI 参数） |
| guard-command | 高危命令与危险参数拦截 | —— |

两者重叠在「删除」语义，但 guard-delete 站在代码构造视角，guard-command 站在命令/参数执行视角；一个包重点在源码静态分析，一个包重点在命令字符串与参数模式。
