# 统一立场与诚实边界

## 一、立场：看清后果再决定，不硬禁止

本系列每条护栏都坚持同一立场——**看清后果再决定，不是替你拍板**。对依赖护栏尤其如此：

- 如果把「发现风险依赖」直接变成「报错、禁止合入、卡死 CI」，开发者会找到更糟的绕过方式：把依赖 vendored 进黑箱、写死 commit、关掉完整性校验。这些绕过让风险更隐蔽、更不可审计。
- 正确的做法是：把风险量化成「依赖风险指数 + 可治理性 + 避免工时」，让人看清代价后自己决定。极端风险才建议「禁止合入」。

这与 guard 系列其他成员（command 危险参数、delete 破坏性操作、network 外联、privacy PII）完全一致。

## 二、可治理性维度

依赖风险是否「可治理」，是这条护栏的专属维度：

- **可治理**：存在明确修复路径——升级到安全版本、替换为维护中包、加锁文件、换 https 源、关掉 install scripts。
- **不可治理**：需要人工决策、暂无明确修复（例如某个深度嵌入且停止维护的包被发现投毒，要评估替换成本）。

本工具默认把命中都标记为「可治理」，因为清单里列的几类风险都有标准处置动作；真正需要人拍板的，往往落在「来源可信」层（自定义源是否受信）这种无法自动判断的场景。

## 三、诚实边界（不糊弄）

1. **只做静态检测**：读清单与安装配置，不解析真实依赖树，不知道运行时实际装了哪些版本。
2. **不实际拦截安装**：决策权在你；工具只出报告。
3. **不承诺 100%**：变量改名、间接引用、vendored 黑箱、私有 registry 白名单都会漏；个别普通包名（如 `@babel/core` 这类公开 scoped 包）可能被启发式误报，需人工复核。
4. **不评估漏洞利用难度**：只量化静态可见风险，是否为 0-day、是否已被利用，由人判断。
5. **自定义源不判死**：`.npmrc`/`pip.conf` 指向非默认源一律提示人工确认，而非直接定罪——受信私有源同样是这个写法。

## 四、与系列其他护栏的衔接

| 护栏 | 管什么 | 本护栏的衔接点 |
|---|---|---|
| guard-skill | 装包前的供应链背调 | 本护栏是它的「持续性」补位（已装依赖的长期扫描） |
| guard-secret | 密钥字段 | 投毒安装脚本常借机密外泄，二者互补 |
| guard-network | 外联通道 | 投毒包常借外联回传，二者互补 |
| guard-privacy | PII 字段 | 投毒包常借 PII 外传，二者互补 |

单点银弹不存在。本工具是多层防御里「依赖入口」这一层，配合其他护栏形成纵深。
