# 依赖溯源：SLSA 与 SBOM

## 一、为什么依赖需要被「看清」

现代软件几乎没有从零写起的。一个应用动辄引入数十到上千个开源依赖，而这些依赖又各自带着自己的依赖。这条「依赖树」的任一层被投毒，后果都会顺流影响到你。问题在于：绝大多数团队对自己到底装了哪些包、哪个版本、来自哪个源，并没有一份可审计的清单。

SLSA 与 SBOM 正是为解决这个问题而生，它们也是本工具的理论底座。

## 二、SLSA（供应链溯源框架）

SLSA（Supply-chain Levels for Software Artifacts）把供应链安全分成源码、构建、制品三层，逐级强制：

- **L1**：构建过程可记录（有 provenance）。
- **L2**：构建环境防篡改、依赖清单完整。
- **L3**：构建在受防篡改的平台上执行。
- **L4**：构建过程本身可审计、可复现。

本工具对应的，是 L1-L2 的「**依赖清单可审计、构建可复现**」这一前提。一个连自己依赖都列不清、版本都锁不住的项目，谈不上更高级的供应链保障。

## 三、SBOM（软件物料清单）

SBOM（Software Bill of Materials）要求每个软件制品都能列出其全部组件与版本，源自 NTIA 的最小元素指南与行政命令要求。它的价值在出事时最明显：

- 某依赖曝出 0-day，你能在一分钟内查出「谁在用、在哪个版本」。
- 发现投毒包，你能反查「它被哪些制品引入、影响多大」。

本工具扫出来的「命中清单」本质上就是一份**轻量 SBOM 缺口视图**——它不关心组件本身有没有 CVE，而是关心「这些组件是怎么被引入和处置的」。

## 四、与本工具的关系

| SLSA/SBOM 要求 | 本工具对应检测 |
|---|---|
| 依赖清单完整、可审计 | DEP-PIN-LOOSE（浮动版本不可审计）、DEP-NO-INTEGRITY（无哈希不可校验） |
| 构建可复现 | DEP-FORK-PIN（锁分支/commit 不可复现） |
| 来源受控 | DEP-GIT-URL、DEP-HTTP-SOURCE、DEP-UNTRUSTED-REGISTRY、DEP-PROTOCOL-HIJACK |
| 组件可信 | DEP-CONFUSION、DEP-TYPOSQUAT、DEP-EOL-KNOWN、DEP-INSTALL-SCRIPT |

理论不是装饰。每一个规则背后都可溯源到 SLSA 或 SBOM 的一条硬要求，这正是工具「敢说自己在做供应链安全」的底气。
