# guard-dependency 常见问题（场景 → 话术）

## 1. 它和普通漏洞扫描（如 npm audit）有什么区别？
npm audit 查「已知 CVE」，本工具查「供应链投毒与配置风险」——浮动版本、git 源、明文 http 源、安装钩子执行代码、依赖混淆命名、无完整性哈希。两者互补：CVE 看「这个版本有没有公开漏洞」，本工具看「这个引入方式本身安不安全」。

## 2. 为什么不直接禁止有风险的依赖合入？
硬禁止会逼人把依赖 vendored 进黑箱、写死 commit、关掉哈希校验——更隐蔽、更不可审计。本工具立场是看清后果再决定：极端风险才建议禁止合入，其余让你拿着「依赖风险指数 + 可治理性 + 避免工时」自己拍板。

## 3. 扫描报了一堆中危，我要全修吗？
中危（浮动版本、无哈希、锁分支）是可治理的「卫生习惯」缺口，建议补但不阻断。真正要拦的是高/极端：已知投毒版本、typosquatting、依赖混淆、安装钩子执行代码、明文 http 源。

## 4. 我的私有源 registry 被标成高危，是不是误报？
不一定是误报，但本工具对「自定义源」一律提示人工确认、不直接判死——受信私有源同样是这个写法。你需要确认：这个源是组织下发的受信源，还是某次手滑加的命令级自定义源。

## 5. DEP-CONFUSION 把我的 @babel/core 标红了，怎么办？
公开 scoped 包（如 @babel/core）是合法包，本工具的依赖混淆启发式只认 `internal-/private-/corp-/mycompany-/acme-` 这类内部命名前缀。如果误报，说明你的包名恰好撞了内部命名约定——核对是否真的走了公共源即可，或在白名单语境下放过。

## 6. 安装脚本（postinstall）真的那么危险吗？
历史上 event-stream 后门就是借 postinstall 落地的。脚本一装就跑作者代码，等于把执行权交出去。生产环境建议 `npm ci --ignore-scripts`，确需脚本的包人工审计后开白名单。

## 7. 锁文件有了，为什么还说「无完整性哈希」？
有锁文件≠有哈希。npm 默认带 integrity（sha512），但某些配置、或手动改过的 lockfile、或 pip 没开 hash-checking 时，resolved 地址旁看不到哈希，就无法校验下载内容是否被篡改。本工具对「有地址无哈希」单独报警。

## 8. 它能不能发现我项目里的幽灵依赖？
本工具会提示代码里 `import`/`require` 了第三方包但清单可能未声明的情况（需人工核对清单）。它不做跨文件精确比对，所以这是「提示」而非「定罪」——目的是让你去查这个包到底声明没。

## 9. 误报太高怎么办？
三类常见误报：①公开 scoped 包撞内部命名（见 Q5）；②测试/示例文件里的依赖写法（白名单语境 `@test`/`示例` 等会自动放过）；③私有源被标高危（见 Q4）。其余可按项目实际在引擎全局 `ALLOW_KEYWORDS` 常量里加合理词。

## 10. 升级与回退怎么搞？
升级：改引擎常量（白名单、严重度权重）、`resources/rules.json`（规则库）、量化参数后重打包。回退：保留旧 zip，覆盖即可回到上一版。本工具不做破坏性改动，随时可回退。

## 边界提醒
本工具只做静态检测，不解析真实依赖树、不实际拦安装、不承诺 100%。它是多层防御里「依赖入口」这一层。
