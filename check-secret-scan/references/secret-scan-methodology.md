# 密钥明文快检方法论（check-secret-scan）

本文件说明 check-secret-scan 能判定什么、不能判定什么，以及各类规则背后的取舍。

## 一、能确定性判定的（本包范围）

1. PEM 私钥块：匹配 `-----BEGIN ... PRIVATE KEY-----` 这种 unambiguously 是私钥的文本块。一旦进仓库就等于私钥泄露，定为极端级。
2. 已知前缀明文密钥：从 resources/secret-patterns.json 加载一组高置信前缀（AWS `AKIA`、GitHub `ghp_`、Slack `xox`、Google `AIza`、GitLab `glpat-`、OpenAI `sk-`、JWT `eyJ` 等），内容命中即判定为真实密钥泄露，定为极端级。
3. 通用硬编码凭证：`password/secret/token/api_key/access_key/client_secret` 等被赋成字面值（带引号、长度≥4），定为高级。
4. URL 内嵌凭证：地址里出现 `user:pass@` 形态（如 `协议头://user:pass@host`），定为高级。
5. 被提交的 .env 文件：文件名命中 `.env`，定为中级（里面通常装真实凭证）。

## 二、不能判定、也不假装能判定的

- 无前缀的高熵随机密钥（纯随机字符串、没有可识别前缀）：本包不做全量熵分析，会漏报。那是 guard-secret 深度版或专业密钥扫描器的活。
- 经环境变量 / 密钥管理器正确注入的凭证：本包不运行时读取，只看静态文本，正常注入不会误报。
- 密钥是否「已经在别处泄露」：那是历史泄露库的事，超出静态快检。

## 三、严重度设定

- 极端：明文私钥块、已知前缀明文密钥。这两类一旦发布即等于泄露，故定为极端级并建议阻断（退出码 4）。
- 高：硬编码凭证、URL 内嵌凭证。可读、可爬取，但不如私钥致命。
- 中：.env 被提交。高概率雷区，但内容可能只是占位。
- 低：已接入专业密钥扫描工具（安全变体，仅鼓励信号）。

## 四、为什么用「前缀 + 模式」而非实时检测

实时密钥检测需要联网或接入平台、慢、难进 CI、结果不稳定。本包只用不需语义理解的确定性模式，因此可重跑、可留证据、可进 CI，专门拦住「明文私钥 / 已知前缀密钥 / 硬编码凭证」这类一眼就能揪的泄露。

## 五、如何扩展前缀库

直接编辑 resources/secret-patterns.json，追加 `{"name": "厂商名", "pattern": "正则"}` 即可，引擎在每次扫描时实时加载，无需改代码。
