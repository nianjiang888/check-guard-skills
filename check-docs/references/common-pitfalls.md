# 常见误报与边界（check-docs）

本文件列出发包前已知、且已做规避处理的几类边界，便于使用者理解「为什么有时没报、为什么有时报了但可关」。

1. 声称完成却未完成的边界：只要「完成声明 + 未完成标记」同时出现即判定（中）。这是有意为之——这类形态几乎必然让文档与代码脱钩。若你的文档确实需要同时出现两词（如变更日志），可把该规则严重度调低或在 rules.json 里收窄关键词。
2. 占位符的边界：DOCS-PLACEHOLDER 用 {{}}/TBD/待补充/占位符/coming soon 命中，但仍可能在文档刻意举例（如「模板里写 TBD」）时误报。测试文件命名带 test_/example/sample 会被自动跳过；也可在 rules.json 里调整。
3. 死文件引用的边界：引擎只在扫描根内按相对路径解析，找不到即报高。若被引文件确实在仓库其他位置，属路径写法问题，调整引用即可消除，非误报。
4. 引用逃出仓库根的边界：DOCS-ESCAPE-REF 只判 ../ 逃出仓库根，正常仓库内相对引用不报；它不影响运行，但属结构隐患，故定中级。
5. 标题层级跳跃的边界：仅按「相邻标题层级差 >1」判定，不读章节语义。即便只有两级标题但跳了级也会报——因为结构断裂本身就是可读性问题。
6. 已接入文档同步的边界：DOCS-CLEAN 仅做鼓励信号，不计入发现项、不提升判定等级；它存在的意义是「你已经做了该做的，给予正向标记」。
7. 测试 / 示例文件：文件名含 test_/example/sample，或内容带明确测试标记（fixture/测试专用示例）会被跳过，避免把示例里的「故意缺陷」报成真实问题。真实文档即使正文出现 example 等词也不跳过，宁可在示例上多扫，也不在真实文档上漏报。
8. 合规红线：本包所有源文件与压缩包均不含明文协议头、真实地址、绝对路径、BOM 与 CRLF，可安全上架分发。
