# guard-secret 常见问题（按你会怎么问组织）

## 我要提交代码了，怎么确认没把密钥带上去？
把整个项目目录交给 `python guard.py scan <目录>`。它会跑三层检测，最后给一个判定：低/中可直接提交，高/极端会拦截（退出码 4）并告诉你哪一行、是什么类型的密钥。

## 它说"高"，我就绝对不能提交吗？
"高"的语义是"拦下，需人工确认后再决定"。意思是命中了高危密钥格式（比如 API Key 或数据库口令），你得看清具体是哪条、是不是真密钥、有没有进过历史。不是机器替你拍板，是机器替你看见风险。

## 为什么要算"熵"？正则不够吗？
不够。正则只认得已知格式（AWS/JWT/Slack…），团队自造的内部 token 它完全看不见。熵层不认格式、只认"够不够随机"，正好兜住正则的盲区。但熵会被 base64 测试数据淹没，所以还要叠第三层上下文白名单。三层组合才能逼近生产可用的精度。

## 密钥写在代码里，删掉那行就行了吗？
不行。Git 历史里凭据仍在，真正的正确动作是**立即轮换凭据**（吊销旧密钥、签发新密钥）。扫描报告会明确标注"疑似已泄露，请轮换"，而不是只说"删掉"。

## 它能不能 100% 拦住泄露？
不能，也不该这么宣传。密钥检测没有单点银弹，业界主流扫描器公开文献都承认生产调优后精度约 90–95%。guard-secret 的诚实立场是三层组合降低漏报与误报，而不是承诺神话。

## 误报怎么办？
上下文白名单已经放过 `example`/`test`/`dummy`/`placeholder` 等示例串，`node_modules`、`*.lock`、`*.min.js` 等噪声源也直接跳过。高熵但无凭据上下文的串只报"中危需人工确认"、不阻断。不要把告警当耳旁风，也不要一见告警就全点忽略——告警疲劳会杀死安全产品。

## 和 guard-skill 有什么区别？
guard-skill 管"装第三方包之前的入职背调"（审查别人的包），guard-secret 管"自己代码里的密钥字段"（审查自己的仓库）。一个对外审查，一个对内体检。

## 扫描规则我能改吗？
能。`resources/rules.json` 是规则库，新增/调整正则规则或熵阈值改这个文件即可，不用动引擎代码。每条规则含 id / name / category / severity / pattern。
