# 密钥检测的三层管线与诚实边界

> guard-secret 的原创量化点不在某条规则，而在"三层互补"的工程设计，以及把"拦不住什么"写进文档的诚实立场。本篇拆解这三层，并对照 CWE 与业界实践说明边界。

## 一、问题：没有一种方法能单挑

密钥泄露检测有三条互不相同的路径，各有死穴：

| 方法 | 能抓什么 | 必漏什么 |
|---|---|---|
| 正则匹配已知格式 | AWS/GCP/Slack/JWT 等标准密钥，误报极低 | 团队自造、非标准命名的内部 token |
| 熵值（随机性） | 任意格式的高随机串，召回广 | 被 base64 测试数据/哈希淹没，误报高 |
| 上下文/语义 | 能区分"这是真密钥"还是"这是示例" | 单独用几乎抓不到任何东西 |

仅用其一都会走向两个坏结局之一：**漏报**（真密钥溜过去）或**误报**（正常代码天天弹告警，团队学会点"忽略"，真泄露也被忽略）。告警疲劳是安全产品最致命的死法。

guard-secret 的做法是三层串联，每层补上一层的洞。

## 二、第一层：正则（精度层）

匹配业界标准化的密钥格式：

- 云凭据：AWS 访问密钥 `AKIA` + 16 位、`aws_secret_access_key`、GCP 服务账号私钥 JSON、Azure 连接字符串。
- 私钥：`-----BEGIN ... PRIVATE KEY-----` 头。
- 密码/连接串：`password = "..."`、数据库 `scheme://user:pass@host`。
- API/令牌：API Key 赋值、Bearer/JWT、Slack `xox*`、GitHub `ghp_*`、Google `AIza`、Stripe `sk_live_*`。

这一层的价值是**低误报**——匹配上了基本就是密钥。但它的盲区是"不认识的形状"。一个团队把内部 token 命名为 `my_internal_thing` 且长得随机，正则完全看不见。这正是第二层的活。

## 三、第二层：熵值（召回层）

对任意长度 ≥20 的字母数字串计算香农熵，超过阈值即标记（详见 `shannon-entropy.md`）。它不认识格式，只认"够不够随机"，因此能兜住第一层漏掉的自造密钥。

但熵会被正常的高随机数据误伤：lockfile 里的哈希、测试用的 base64 样本、UUID。所以熵层标记出来的，必须再经过第三层筛选。

## 四、第三层：上下文 + 白名单（降误报层）

对每一处命中（无论来自正则还是熵），取其前后各约 60 字符的上下文窗口，做两件事：

1. **凭据关键字提升置信**：窗口里出现 `key`/`secret`/`token`/`password`/`credential` 等词，说明这串"被当密钥用"，置信度升为"高"，命中即按高/极端处理（拦下）。
2. **白名单放过**：窗口里出现 `example`/`test`/`dummy`/`placeholder`/`your-key-here`/`xxxx` 等词，判为示例或占位，直接放过，不当作泄露。

此外，路径级白名单直接跳过 `node_modules`、`*.lock`、`*.min.js`、`.env.example` 等已知噪声源。

三层叠加的结果：标准密钥（正则命中 + 上下文）→ 高/极端拦下；自造随机密钥（熵命中 + 上下文）→ 高拦下；高熵无上下文（可能是哈希）→ 只报"中危需人工确认"不阻断；示例串 → 静默放过。既保住召回，又把误报关进笼子里。

## 五、与 CWE 的对齐

密钥硬编码是 CWE-798（Hard-coded Credentials），常年位居高危榜。把密钥写进代码、又提交进版本库，等于把钥匙插在门上。guard-secret 的全部规则都围绕 CWE-798 及其近亲（CWE-259 硬编码口令、CWE-321 硬编码加密密钥）展开。

**关键纠正（必须写进报告）**：密钥一旦进过 Git 历史，"删掉那一行"没用——历史里仍在。正确动作是**立即轮换凭据**（吊销旧、签发新），而非仅清理代码。本工具的扫描报告会明确标注"疑似已泄露，请轮换"。

## 六、诚实边界（不吹 100%）

业界主流扫描器（gitleaks、TruffleHog、GitGuardian）公开文献均承认：在生产环境调优后，密钥检测精度约在 **90–95%**，不存在单点银弹。guard-secret 同样诚实声明：

- 纯正则漏自造内部 token；
- 纯熵值被 base64 测试数据淹没；
- 三者组合才能逼近 90–95%，且仍可能漏（精心构造的低熵弱密钥）或误（未覆盖的私有格式）。

把"拦不住什么"写进文档，反而是评审加分项——它证明作者懂这个领域的真实难度，而不是在吹一个不存在的神话。
