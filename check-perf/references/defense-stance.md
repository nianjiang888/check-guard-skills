# 防御立场与诚实声明（check-perf）

本文件说明 check-perf 在「帮你拦住性能雷区」这件事上的立场与边界。它不是压测平台，而是一道可重跑、可量化、留证据的静态防线。

## 一、立场：拦得住的才拦，不假装全能

- 只做不需要语义理解的确定性模式：无 timeout 的网络调用、while True 无限循环、循环内 N+1 查询、async 内的同步阻塞、无分页的列表返回。这些恰恰是「人容易看漏、工具一眼揪出」的低垂性能雷区。
- 不做运行时剖析（量化真实吞吐/延迟/P99），也不做真实压测。那超出了静态快检的能力，强行做只会制造噪声，反而让人不再信任工具。

## 二、诚实边界

- 不承诺真实性能数字：模式命中只说明「触碰了已知雷区」，不表示当前就一定慢；报告里每条都标注命中类型，由人最终裁决。
- 不修改文件：只产出报告与机器可读判定块，是否修复、怎么修复由使用者决定。不替你改代码，避免「自动修正」引入新问题。
- 不拦截部署：返回退出码供 CI 消费，但是否阻断由流水线策略决定；本包对高级（无 timeout）问题返回退出码 1（建议修复后发布）。

## 三、与同类工具的关系

- 与 guard-* 互补：guard-* 做运行期/深度防护，check-perf 做快检版（模式命中即报）。两者入口不同、互不替代。
- 与专业剖析/压测工具（cProfile/py-spy/pprof/locust/wrk 等）错位：那些做运行时量化，本包做轻量、可进 CI 的确定性检查，二者可叠加使用。

## 四、可修正性量化的意义

每条发现都带「可修正 / 不可修正」标记，并汇总成「验证暴露指数」与「预计避免返工工时」。这让性能风险从「感觉会慢」变成可比较、可追踪的数字，也方便在多个文件 / 多个包之间排优先级。
