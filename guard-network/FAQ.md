# guard-network 常见问题（场景 → 话术映射）

**Q1：我的代码就是调个第三方 API，也会被拦？**
不会直接拦。普通 `requests.get` 读数据不在规则内；只有**出站 POST/PUT 带数据体**（`NET-EGRESS-POST`，高）和**编码后外发**（`NET-EXFIL-B64POST`，高）会提示你确认接收方可信、走白名单。合法业务勾选"已确认接收方 + 走白名单 + 留审计"即可放行。

**Q2：报了"极端"，我该怎么办？**
极端意味着出现 `NET-EGRESS-SOCKET`（原始 socket 直连外部）、`NET-TUNNEL-REVSHELL`（反弹 shell）、或 `NET-C2-KNOWN`（超长随机子域 DGA 特征）。这三类几乎肯定是危险出口，建议**禁止上线**，先加出口白名单/审计/TLS 校验再说。

**Q3："可阻断/不可阻断"到底差在哪？**
可阻断 = 应用层出口网关/白名单大概率能拦（如普通 HTTP 外联）；不可阻断 = 需要内核或网络层手段才能管（原始 socket、DNS 隧道、反弹 shell）。标"不可阻断"不是让你禁止，而是提醒你要更深一层的防护（网络 ACL、eBPF 观测、DNS 监控）。

**Q4：我的代码里有个长随机子域被标 C2，但它是合法 CDN 指纹，怎么办？**
`NET-C2-KNOWN` 是启发式，会把个别合法长随机串误报。它的定位是"提示你确认"，不是定性。确认合法后把该串放配置并加说明，或整体按白名单语境处理即可。不要在代码里硬删功能来"骗过"扫描。

**Q5：DNS 隧道那条怎么理解？**
`NET-DNS-EXFIL` 抓"把 base64/hex 数据拼进 DNS 查询"的写法。很多网络不对出站 DNS 做深度检测，所以这类外泄特别隐蔽，标为不可阻断（需 DNS 层监控）。

**Q6：sleep 之后发请求就一定是 C2 吗？**
不一定。`NET-C2-BEACON` 只抓"sleep 后紧跟外联"的紧邻形态作可疑信号。轮询第三方接口也会这样写——它提示你"这是周期性回连，确认业务必要并走白名单"。

**Q7：这个工具能拦住数据外泄吗？**
不能，也不试图拦。它只做**发布前的静态提示**。真正的出口安全靠运行时出口过滤 + 审计 + 监控。本工具是那之前的一盏灯，让你写代码时就想清楚出口该往哪走。

**Q8：误报太多怎么办？**
规则本身已分层降噪（安全变体层只鼓励不命中、上下文白名单放过示例/教学语境）。若仍有项目级误报，优先用"确认接收方 + 走白名单 + 留审计"的写法让工具识别为安全变体，而不是删功能。

**Q9：和 guard-secret、guard-command 什么关系？**
secret 管"密钥别硬编码"（防凭证泄露），command 管"危险命令别跑"（进程行为），network 管"跑起来的代码别往外连"（网络行为）。三者互补：凭证不泄露、危险命令不跑、出口有护栏，才构成闭环。

**Q10：升级或回退怎么操作？**
升级：改引擎常量 `ALLOW_KEYWORDS`、规则库 `resources/rules.json`、量化权重（`SEV_WEIGHT`/`avoided_exfil_hours`）后重新打包。回退：保留上一版 zip 直接覆盖即可，规则与引擎解耦，回退不影响已生成的报告。
