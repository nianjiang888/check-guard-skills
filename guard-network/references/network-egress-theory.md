# 外联过滤与数据外泄：理论与检测立场

## 1. 为什么要管"出口"

安全建设长期重"进"轻"出"：防火墙、WAF、入侵检测都在拦外面进来的东西，却很少认真看里面出去的。但数据外泄（exfiltration）恰恰发生在出口——一旦敏感数据离开边界，损失就定了，事后取证成本高得离谱。

MITRE ATT&CK 把外泄单列一阶，给出两条最贴合代码静态检测的路径：

- **T1041 Exfiltration Over C2 Channel**：复用已建立的 C2 通道外泄，流量混入正常回连，难以区分。检测重点在回连频率与目标。
- **T1048 Exfiltration Over Alternative Protocol**：走非标准协议（DNS、ICMP、TLS 伪装、甚至第三方云存储 API）外泄，规避基于端口/应用的过滤。DNS 隧道是其中成本最低、最常被忽视的一种。

## 2. 出口过滤（Egress Filtering）作为基础设施

CIS Critical Security Controls 把出站流量管控列为边界安全的基本盘。落到工程上分三层：

1. **应用层**：统一出口网关 / SDK，所有外联走白名单域名 + TLS 校验 + 审计日志。这一层能拦住绝大多数 `requests.post` 型外泄。
2. **网络层**：防火墙 ACL、eBPF 观测，拦原始套接字、异常端口、非常规 TLD 的 DNS。
3. **数据层**：DLP 对出站内容做敏感字段识别，编码（base64/hex）不等于安全。

本工具的定位是**第 0 步**：在代码发布前静态扫一遍外联通道，把"哪些出口需要护栏"摊开给人看。它不替代上述任何一层，而是帮你在写代码时就想清楚出口。

## 3. 为什么是"看清后果再决定"而不是硬禁止

硬禁止（比如一刀切禁掉所有 `socket.connect`、禁掉所有外联）在工程上不可行，也会逼出更坏的结局：

- 正常业务需要合法外联（调用第三方 API、上报埋点），全禁等于不干活。
- 真想外泄的人会把通道藏更深：流量加密、域名分段、借白名单内的跳板二次转发。越禁止，越隐蔽，越难检测。

所以本工具只做**量化与提示**：算出外联暴露指数、标出可阻断/不可阻断、给出避免损失工时，把决策权交还人。这与系列其他包（cost/memory/command）立场一致——护栏的价值在"让人看清"，不在"替人拦"。

## 4. 量化模型来源

- 严重度权重（极端 100 / 高 40 / 中 12 / 低 3）与"安全控制价值量化（避免工时）"沿用系列统一口径，参考 Nygard 熔断器与 SRE 错误预算的"可量化成本"思路：把"没发生的事故"折算成可感知的数字，让安全投入有依据。
- 可阻断性维度是网络域专属：区分"应用层能拦"（可阻断）与"需内核/网络层才能管"（不可阻断），避免把 raw socket 和正常 API 调用混为一谈。
