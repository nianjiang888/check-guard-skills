# 设计立场与诚实边界（guard 系列统一）

## 立场：看清后果再决定，不硬禁止

guard 系列每个包都守同一条线：**护栏的价值在让人看清风险，不在替人拦**。具体到 guard-network：

- 外联是双刃剑。合法业务（调第三方 API、上报埋点、拉取配置）需要外联，全禁等于不干活。
- 硬禁止会逼出更隐蔽的绕过：流量加密、域名分段、借白名单内跳板二次转发。越禁止，越难检测，结局更坏。
- 所以本工具只做量化与提示：外联暴露指数、可阻断/不可阻断、避免损失工时，决策权交还人。

## 诚实边界（必须写明，不承诺 100%）

1. **只静态检测，不实际拦任何流量。** 工具跑完，代码该外联还外联。拦不拦是你的运行时策略。
2. **对运行时真实外联无感知。** 代码是否真被运行、网络是否放行、目标是否可达——本工具不知道。
3. **启发式正则，漏报与误报并存。** 加密隧道、域名分段、变量延迟拼装都会漏；个别合法长随机串会被 `NET-C2-KNOWN` 误报。规则仅作提示。
4. **可阻断性不是保证。** "可阻断"指应用层出口过滤大概率能拦；一旦代理被绕过，仍可能失效。
5. **不评估数据价值。** 外泄后果的严重性取决于数据敏感度，本工具只量化静态可见风险。

## 退出码约定（全系列一致）

| 码 | 含义 |
|----|------|
| 0 | 通过（低危或无命中） |
| 1 | 参数错（缺目录 / 路径不存在） |
| 2 | IO·运行错（资源解析失败 / 报告写入失败） |
| 3 | 未知命令 |
| 4 | 已拦截（高/极端风险，建议不要直接上线） |

## 安全控制价值量化

把"没发生的外泄"折算成可感知数字：极端 8h（整机/全量外泄需停机止损与取证）/ 高 4h（单通道定位与封堵）/ 中 1h（补护栏）/ 低 0h。这是 GRC/安全运营的标准做法——用成本语言让安全投入有依据，而非"账本"拟人化包装。

## 与系列其他包的衔接

- 与 guard-secret：secret 管"密钥字段别硬编码"，network 管"数据别从出口溜走"——前者防凭证泄露，后者防数据外泄，互补。
- 与 guard-command：command 管"危险命令别跑"，network 管"跑起来的代码别往外连"——进程行为与网络行为两条线。
- 与 guard-share（规划中）：share 管"整个文件外发前查边界"，network 管"代码里的外联通道"——文件级 vs 代码级。
