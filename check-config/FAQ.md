# check-config 常见问题（FAQ）

| 场景 | 话术 |
|---|---|
| 「我的配置文件在哪都能跑，还要检查吗？」 | 本地能跑不等于生产能跑。配置错是最隐蔽的线上故障源，check-config 在部署前替你扫一遍低垂的坑。 |
| 「它会不会误报我的示例配置？」 | 不会。文件名含 test_/example/sample 或内容含 example/sample/demo/placeholder/your_/xxxx 等会被跳过；明文密钥规则也排除了占位符值。 |
| 「发现明文密钥，改掉文件就行了吗？」 | 不够。写进文件的密钥视为已暴露，正确做法是移到环境变量并**轮换**密钥——所以本包标为「不可修正」。 |
| 「退出码 4 是什么意思，它会拦我部署吗？」 | 4 = 发现极端级问题（如明文密钥），仅「建议阻断」。是否真阻断由你的 CI 策略决定，本包不替你拦。 |
| 「端口填成 99999 为什么会报高？」 | 端口合法范围是 1–65535，超范围服务起不来且难定位，属于上线即故障的坑。 |
| 「生产开 debug 为什么是中而不是极端？」 | 它泄露内部信息、拖慢性能，但通常不直接导致数据事故，故定中级；极端留给明文密钥这类。 |
| 「和 guard-secret 有什么区别？」 | guard-secret 是深度安全防护（分级+阻断建议），check-config 是快检版（扫一眼报出来）。两者入口不同、互补不替代。 |
| 「支持哪些配置格式？」 | 只要是文本配置（ini/yaml/toml/json/env/properties 等）都扫，按通用键值模式匹配，不挑框架。 |
| 「扫描太慢/太多文件怎么办？」 | 直接指到具体配置目录或文件即可，不必扫整个仓库。 |
| 「升级后规则变了，旧报告还作数吗？」 | 以当前版本 rules.json 为准。升级时本包会保留旧版说明，建议按新规则重跑一次。 |
