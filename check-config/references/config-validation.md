# 配置校验的方法论依据

配置错误是生产故障的头号来源之一。check-config 的判定逻辑建立在以下已被工程界广泛接受的原则上：

## 1. 配置与代码分离（十二要素应用）

十二要素应用（2011）明确：配置必须存储在环境变量中，绝不写进配置文件或代码。理由是代码可开源、可复用，配置不可。一个把数据库密码写进 `config.ini` 的项目，一旦仓库泄露，凭据随之泄露。

check-config 据此把「明文密钥」列为极端级、且标为「不可修正」——因为写进文件的密钥即使事后删掉，也视为已经暴露，正确做法是轮换。

## 2. 加载即校验（Schema 校验）

配置在应用启动加载时应经过结构化校验：必填项是否存在、字段类型是否正确、枚举值是否合法、数值是否越界。错误应在启动期就暴露，而不是运行到某条分支才崩溃。

check-config 的「端口超范围」「日志级别非法」「连接配置缺鉴权字段」都来自这一思路：用静态文本规则逼近「加载即校验」能拦住的那部分错误。

## 3. 环境一致性

开发、测试、生产环境应尽量一致；生产环境不得开启调试开关、不得混用开发配置。check-config 的「生产开 debug」规则即据此。

## 4. 为什么是静态检查而非运行时

静态检查在部署前就能跑、可重跑、可进 CI、可留证据，成本远低于「上了生产才发现」。它不替代运行时配置校验，而是把「部署前最后一次人工复核」标准化。
