# 防御立场与诚实声明（check-api）

本文件说明 check-api 在「帮你看住 API 契约缺口」这件事上的立场与边界。它不是规范深度校验器，而是一道可重跑、可量化、留证据的静态防线。

## 一、立场：拦得住的才拦，不假装全能

- 只做不需要语义理解的确定性模式：漏 responses、缺错误响应、GET 带 body、无鉴权声明、无 description。这些恰恰是「人容易看漏、工具一眼揪出」的低垂契约缺口。
- 不做语义级 schema 校验（发现「字段类型错/必填漏标」），也不做引用解析与跨文件关联。那超出了静态 lint 的能力，强行做只会制造误报，反而让人不再信任工具。

## 二、诚实边界

- 不承诺 100% 准确：声明级检查在文本里恰好出现关键词时可能误报；报告里每条都标注命中类型，由人最终裁决。
- 不修改文件：只产出报告与机器可读判定块，是否修复、怎么修复由使用者决定。不替你改接口定义，避免「自动修正」引入新问题。
- 不拦截部署：返回退出码供 CI 消费，但是否阻断由流水线策略决定；本包对高级契约问题返回退出码 1（建议修复后发布），极端级退出码 4 保留与系列一致。

## 三、与同类工具的关系

- 与专业 OpenAPI linter（语义级校验）错位：那些做深度 schema 校验 + 引用解析，本包做轻量、可进 CI 的确定性检查，二者可叠加使用。
- 与 check 系列其他成员互补：check-config 查配置项、check-links 查引用关系、check-spelling 查文字、check-secret-scan 查明文密钥，check-api 查接口契约缺口。

## 四、可修正性量化的意义

每条发现都带「可修正 / 不可修正」标记（本包规则均「可修正——补定义即可」），并汇总成「验证暴露指数」与「预计避免返工工时」。这让接口风险从「感觉不规范」变成可比较、可追踪的数字，也方便在多个文件 / 多个包之间排优先级。
