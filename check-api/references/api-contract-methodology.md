# API 契约校验方法论（check-api）

本文件说明 check-api 能判定什么、不能判定什么，以及各类规则背后的取舍。

## 一、能确定性判定的（本包范围）

1. 漏写响应结构：声明了 get/post 等操作却没写 `responses`，调用方不知返回什么，定为中级。
2. 缺错误响应：写了 `responses` 却只有 `200`，没有 `4xx/5xx`，客户端无法处理异常，定为中级。
3. GET 带请求体：出现 `requestBody` 挂在 `get` 下，GET 语义不应有体，通常是动词用错，定为高级。
4. 全程无鉴权：定义了 `paths` 却没有任何 `security/authorization/apiKey` 等鉴权声明，接口裸奔，定为中级。
5. 缺描述：定义了 `paths` 却没有 `description`，消费者看不懂用途，定为低级。
6. 已接规范工具：命中 `openapi/swagger/pydantic/fastapi` 等，属正向信号（safe 层，仅鼓励，不计入发现项）。

## 二、不能判定、也不假装能判定的

- 字段类型错误、必填漏标、枚举越界：本包不做语义级 schema 理解，会漏报。那是规范深度校验器或专业 OpenAPI linter 的活。
- 鉴权是否「真的有效」：本包只静态看有没有鉴权声明，不验证鉴权方案是否健全。
- 接口「是否已经上线并在运行」：那是运行时监控的事，超出静态契约校验。

## 三、严重度设定

- 高：GET 带 requestBody。语义错用，会影响缓存/代理/网关对请求的理解。
- 中：漏写 responses、只有 200 缺错误响应、无鉴权声明。契约缺口明显，调用方易踩坑。
- 低：缺 description；已接规范工具（仅鼓励）。可读性底线信号。
- 极端：本包未启用极端级规则；退出码 4 保留与 check-* 系列一致。

## 四、为什么用「模式」而非语义校验

语义级 OpenAPI 校验需要解析完整 schema、做引用解析、跨文件关联，慢且难稳定进 CI。本包只用不需语义理解的确定性模式，因此可重跑、可留证据、可进 CI，专门拦住「漏 responses/缺错误响应/GET 带 body/无鉴权/无描述」这类一眼就能揪的契约缺口。

## 五、如何扩展规则

直接编辑 resources/rules.json，追加 `{"id": "...", "layer": "...", "kind": "regex", "severity": "...", "intent": "...", "req_regex"/"absent_patterns"/"pattern": "...", "recoverable": true, "rec": "..."}` 即可，引擎在每次扫描时实时加载，无需改代码。
