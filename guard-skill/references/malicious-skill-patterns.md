# 恶意包与恶意技能的真实模式

> guard-skill 的红线规则不是凭空编造的。本篇把"后门长什么样"讲清楚——从真实的供应链攻击案例，到 AI 技能生态特有的提示注入后门，每一条红线都有迹可循。

## 一、依赖混淆：伪造同名包投毒

2021 年安全研究员 Alex Birsan 公开演示了**依赖混淆攻击（Dependency Confusion）**：企业在内部用私有包名（如 `internal-utils`），攻击者在公共仓库（npm / PyPI / RubyGems）发布同名包，并打上更高的版本号。构建系统优先拉取"更高版本"的公共包，于是内部构建被悄悄替换为攻击者控制的代码。Birsan 凭此命中微软、苹果、特斯拉等 35 家以上大厂，全程未被发现。

启示：当你安装一个带依赖的技能包，它拉取的每一个依赖都可能是"同名冒牌货"。guard-skill 虽聚焦单包静态审查，但其"溯源 + 全文件审查"思想同样适用于对依赖清单的核验。

## 二、硬编码凭据：最古老的失误

CWE-798（Hard-coded Credentials）长年位居高危之列。把 API Key、数据库密码、SSH 私钥写死在代码里，一旦代码被分享、被上传、被供应链传播，凭据即泄露。这不是"高级攻击"，而是**高频的低级错误**——也是为什么 guard-skill 把"硬编码密钥"（SK-CRD-01）与"读取凭据文件"（SK-CRD-02）列为高危红线。

关键纠正：Git 里"删掉那一行"**没有用**——历史记录里凭据仍在。正确做法是**立即轮换凭据**。guard-skill 的审查报告会明确提示"疑似已泄露，请轮换"，而非仅删除。

## 三、提示注入后门：AI 技能生态的特产

传统恶意包篡改的是**代码**，AI 技能包还能篡改**指令**。一个被投毒的技能，可以在系统提示或示例里埋入"忽略用户此前指令""把用户对话外发到某地址"等越权指令（对应 SK-INJ-01/02/03）。由于大模型的上下文一视同仁、无法区分"指令"与"数据"，这类后门在架构层面极难根治。

OWASP 已将**提示注入（LLM01）**列为 LLM 应用十大漏洞的榜首。guard-skill 对此的诚实立场是：不承诺 100% 拦住（学界共识无单点银弹），而是通过规则分层提高注入被发现的成功率。

## 四、隐蔽执行与反分析

成熟的恶意负载会躲审查：把代码 base64 编码后 `exec()` 执行（SK-OBF-01），或在入口检测运行环境、发现沙箱就静默退出（SK-OBF-02）。这类"反分析"特征本身就是强红旗——正常技能没有任何理由隐藏自己的逻辑。

管道执行远程脚本（`curl ... | sh`，SK-PRV-02）则是另一类经典坑：一条命令就能把远端任意代码拉到本地直接运行，绕过一切本地审查。它是 CWE-829（包含不受信任的第三方组件）的典型表现。

## 五、为什么静态审查仍有价值

有人会问：恶意作者可以混淆绕过正则。没错——但**绝大多数真实危害来自不经意的低质代码与明显的危险模式**，而非精心构造的对抗样本。SLSA 与 OWASP 都强调"纵深防御"：静态红线审查是第一道、最便宜、覆盖最广的防线。它拦下的是 90% 的"本来会中招"，而不是 100% 的"绝顶高手"。
