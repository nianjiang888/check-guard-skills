# FAQ：guard-delete 破坏性操作拦截

## 1. 它会替我拦下危险的 rm -rf 吗？

不会「替」你拦。它的「拦截」是信息层面的：扫描到高危模式时，报告会明确标「建议不要执行」，退出码置 4（已拦截）。但真正点不点回车，永远是你自己。这个设计是刻意的——硬禁止会逼人用 --no-verify、sudo 或裸 shell 绕过，那更糟。

## 2. 我随手敲的命令它能管到吗？

管不到。它只看被扫描的文本文件（脚本、SQL、CI 配置等）里写着的模式。你运行时在终端顺手敲的 `rm -rf`，它感知不到。所以它该和你的操作纪律（二次确认、先备份）配合使用，不是替代。

## 3. 为什么 DELETE 带 WHERE 就降一级？

不带 WHERE 的 `DELETE FROM users` 是整表清空，带 WHERE 只动符合条件的行，破坏范围天差地别。引擎扫到 SQL 删除/清空类规则时，会往后看 400 字符内有没有 WHERE 子句：有就降为「中」并标注影响范围受限，没有就标「疑似全表操作」。这能大幅减少误报。

## 4. blast 真的不会删东西吗？

真的。blast 是干跑预览：对目录只 `os.walk` 统计文件数和总大小，对文件只取大小，全程不调用任何删除/修改 API。报告末尾也写明「本预览仅做统计，不实际执行任何删除/修改命令」。只有 `rm -rf /` 这类极端命令模式会额外给个退出码 4 提示。

## 5. 判定为什么按「优先级链」而不是平均？

因为破坏性操作的危害由最坏那一项决定。一个目录里同时有「rm -rf 构建产物」（可恢复）和「DROP TABLE 无 WHERE」（灾难），平均只会稀释危险。所以规则是：命中任意极端即为极端，否则看最高一级。这避免「九个安全 + 一个致命」被平均成安全。

## 6. 价值账本的「避免 8 小时」是精确测算吗？

不是精确值，是可感知的折算。破坏性操作真正的代价在「删完/推完才看见」——定位影响范围、确认备份、协调恢复、安抚依赖方，综合下来极端约 8 小时、高约 4 小时、中约 1 小时。目的是让安全控制的价值可见，不是做工时审计。

## 7. 误报了怎么办？比如正常的清理脚本被标高危。

正常清理（如定期删构建目录、带 WHERE 的 DELETE）多数会被自动降级或放行：带 WHERE 降一级，示例/教学/虚构语境走全局白名单。如果你有具体场景仍误报，可调整 `resources/rules.json` 的 `allowlist.paths`，或在源码全局 `ALLOW_KEYWORDS` 增删白名单词。注意：白名单在引擎常量里，改 JSON 的 patterns 不生效。

## 8. 它能当团队的安全审计工具吗？

可以当一个轻量环节。把 CI 脚本、迁移 SQL 跑一遍 `scan`，产出的 `blast_report.md` 是可存档证据；多次报告用 `ledger` 聚合成价值账本，便于复盘「这个月拦下了多少先兆」。但它不替代审批流、不替代备份，只是多层防御里的工具层。

## 9. 和系列其他 guard 包什么关系？

平行独立。guard-secret 守凭据、guard-prompt 守提示注入、guard-delete 守破坏性操作——各自一个专业安全域，互不依赖、可单独使用。统一约定是退出码第 4 态=已拦截、纯标准库零依赖、留可审计产物。
