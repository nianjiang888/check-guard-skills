# 设计立场：为什么「看清后果再决定」，而不是「硬禁止」

## 1. 硬禁止会逼出绕过

安全工具最容易犯的错，是把「禁止」当成终点。一旦工具说「这个命令不行」，真实世界里的操作者会立刻找到绕过方式：

- 给命令加 `--no-verify` 跳过校验；
- 用 `sudo` 提权强行执行；
- 干脆不用这个工具，回到裸 shell 直接敲。

结果比我不在场更糟：至少我在场时，操作还被「看见」过一次；绕过之后，连这最后一次看见都没了。所以本包的设计立场从一开始就是——**不硬禁止，只让你看清后果再决定**。

## 2. 这个立场落地成什么

- `scan`：扫描目录里文本化的破坏性操作模式，给出严重度、可逆性、爆炸半径，判定为高/极端时退出码 4（已拦截），但「拦截」是信息层面的——它提示你「别执行」，不替代你的决策。
- `blast`：对一个路径或命令做干跑预览，只数文件、只算大小，**一个字节都不删**，让你在敲回车之前先知道会波及多少东西。
- `ledger`：把多次「拦下的先兆」聚合成价值账本，让安全控制的价值可见。

## 3. 诚实边界（必须说清）

- 我**不**实际执行、拦截或批准任何命令。决策权始终在人。我只在被扫描的文本里看见模式；你运行时随手敲下的命令，我感知不到。
- 我**不**保证 100% 拦住所有灾难。瑞士奶酪模型告诉我们，没有单层防御能挡住一切。我该和备份、版本控制、最小权限、审批流共同构成多层防御，而不是独自扛旗。
- 我**不**替代 `git stash`、定期备份、`rm` 前的二次确认这些基本纪律。它们才是真正的最后一道防线。

## 4. 误报会杀死产品

正因为不硬禁止，误报的代价特别高：如果把「正常删除构建产物」「常规 DELETE 带 WHERE」也报成高危，用户会很快学会忽略我——一旦学会忽略，真正的危险信号也被一起忽略。所以规则设计上：带 WHERE 的 SQL 自动降一级，示例/教学/虚构语境通过全局白名单放行，安全变体（git stash、mv 进回收站）只作鼓励信号、不当命中。宁可在边界上保守，也不制造狼来了。
