# 瑞士奶酪模型与爆炸半径：破坏性操作拦截的理论底座

## 1. 瑞士奶酪模型（Swiss Cheese Model）

1990 年，James Reason 在《Human Error》中提出：复杂系统里没有单一「银弹」防护。每一层防御都像一片瑞士奶酪，上面有孔洞；事故发生的条件是多层奶酪的孔洞恰好对齐，让危险穿透所有层 [Reason 1990]。

把这个模型套到「误删 / 误执行破坏性命令」上，防御链大致是这样的：

| 防御层 | 例子 | 孔洞（可能漏掉的） |
|---|---|---|
| 意识层 | 工程师知道 rm -rf 危险 | 赶工时手快、复制粘贴跑错目录 |
| 流程层 | 审批、双人复核 | 单人值守、临时脚本无人看 |
| 工具层 | 本包（静态检测 + 干跑预览） | 只看得见文本里的模式，看不见运行时即时命令 |
| 系统层 | 备份、版本控制、最小权限 | 备份过期、未跟踪文件没进版本库 |
| 恢复层 | 回滚、灾备 | 无快照、无演练 |

本包定位在「工具层」。它不声称替你挡住一切，而是把「孔洞对齐」在动手之前就显性化——让一次本要静默执行的删除，先过一道检查、先看到爆炸半径。

诚实地说：如果团队把它当成唯一防线，反而更危险。它该和备份、版本控制、最小权限、审批流一起，构成多层防御。

## 2. 爆炸半径（Blast Radius）

「爆炸半径」是站点可靠性工程（SRE）的常用说法，指一次变更的影响范围 [Google SRE Book, 2016]。落到破坏性操作上，可拆成四个可量化维度：

- 影响文件数：blast 子命令直接 `os.walk` 统计，删之前先知道会动多少个文件。
- 影响总大小：以 KB/MB 计，反映数据量。
- 是否可恢复：目标若在 git 版本库内，可 `checkout`/`stash` 还原；若含未跟踪文件或根本不在版本库，删除即丢失。
- 依赖方数量：配置、文档、其他服务是否引用——本包做静态提示，不深究运行时依赖。

四级分级（与引擎严重度对齐）：

- 极端：根目录/主目录级删除，或影响文件 > 1000，几乎不可逆。
- 高：影响非空目录或整表/整库，可逆性低或未知。
- 中：单文件或局部改动，可逆性较高。
- 低：无破坏性操作。
