# 设计立场与诚实边界（guard 系列统一）

## 立场：看清后果再决定，不硬禁止

guard 系列每个包都守同一条线：**护栏的价值在让人看清风险，不在替人拦**。具体到 guard-publish（发布前合规检查）：

- 发布是业务动作——发文章、发工具、发产品说明，都是正常需要，全禁等于不干活。
- 硬禁止会逼人绕开检查走私下渠道发布，那样连「有没有检查过」都不知道，结局更糟。
- 所以本工具只做量化与提示：发布合规指数、可整改性、避免损失工时，决策权交还发布人。

## 诚实边界（必须写明，不承诺 100%）

1. **只静态检测，不实际拦发布。** 工具跑完，内容该发还发。拦不拦是你的发布流程策略。
2. **对内容最终是否真的发布、发到哪个平台、覆盖多少受众无感知。**
3. **不替代法务合规审查。** 合规最终判定需结合业务语境与法务意见；本工具给的是「疑似违规」提示，不是法律结论。
4. **正则启发式，漏报与误报并存。** 换个说法表述同一承诺会漏；个别普通用词会被误报。
5. **不可整改不等于已经泄露。** 它标的是「一旦发布就不可逆」的属性，是预警而非事故认定。
6. **不覆盖所有细分行业特殊监管要求。** 规则只覆盖通用红线（极限词、疗效与收益承诺、个人信息、凭据与内网）。

## 退出码约定（全系列一致）

| 码 | 含义 |
|----|------|
| 0 | 通过（低危或无命中） |
| 1 | 参数错（缺目录 / 路径不存在） |
| 2 | IO·运行错（资源解析失败 / 报告写入失败） |
| 3 | 未知命令 |
| 4 | 已拦截（高/极端风险，建议不要直接发布） |

## 安全控制价值量化

把「没发生的发布事故」折算成可感知数字：极端 8h / 高 4h / 中 1h / 低 0h 的发布后整改与召回工时。这是把合规成本语言化，让「发布前多跑一次检查」的投入有依据，而非拟人化包装。

## 与系列其他包的衔接

- 与 guard-share：share 管「文件发给外部前的内容边界」（发给具体对象），publish 管「内容对外公开发布前的合规」（发给不特定公众）。前者看泄露面，后者看合规红线。
- 与 guard-privacy：privacy 管「代码里 PII 字段的处理」（开发态），publish 管「待发布内容里未脱敏的 PII」（发布态）。
- 与 guard-secret：secret 管「密钥字段的存储与调用」，publish 管「待发布文件里的明文密钥」。
- 与 guard-dependency：dependency 管「依赖的漏洞与投毒」，publish 管「发布物自身的合规」——两者都是发布前门禁，一个看第三方组件，一个看自身内容。
