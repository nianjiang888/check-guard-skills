# 发布清单方法论（guard-publish 理论根基）

## 一、为什么发布前需要一张清单

发布是不可逆动作。文件、工具、内容一旦公开，就被缓存、被转发、被抓取，收不回来。而发布前的疏漏有个共同特点：**每一件单看都简单，组合起来就会漏**。

这正是 Gawande 在《清单宣言》（2009）里描述的困境——在高度复杂的流程里，专家也会因为「以为自己记得」而漏掉关键步骤。解决办法不是让人更细心，而是把必须确认的项写下来，逐项勾掉。

Google SRE 第 8 章讲发布工程时也持同样立场：把人的临场判断从「事后救火」前移到「发布前的自动检查」，让发布这件事可重复、可审计、自动化。

## 二、发布清单的四道关

| 关卡 | 检查什么 | 典型缺口 |
|------|----------|----------|
| 内容合规 | 有没有违法违规表述 | 广告法极限词、疗效承诺、收益承诺 |
| 法律声明 | 该声明的是否声明了 | 免责声明、数据来源、版权署名 |
| 个人信息 | 有没有未脱敏就公开 | 明文身份证/手机号、无隐私政策 |
| 凭据与内网 | 内部东西有没有清干净 | 明文密钥、内网地址、调试残留 |

再加一道元信息关（版本号 / 更新日志 / 授权说明）——它不直接造成事故，但没有它，使用者不知道自己用的是哪一版、改了什么、能不能用。

## 三、合规即代码：把清单变成可重跑的检查

「合规即代码」（Compliance as Code / Policy as Code）的主张是：把合规要求写成机器可检查、可重跑的规则，而不是散落在人脑里的注意事项。

本工具的全部规则即一套可执行的发布合规清单——改规则即改标准，跑一次即一次完整核对，报告即核对证据。相比口头提醒，它有三个好处：

1. **不会漏**：每次跑都走完整套规则，不依赖当时的记忆力与心情。
2. **可追溯**：报告落盘（含机器可读 JSON），事后能说清「发布前检查过哪些项」。
3. **可演进**：规则写在 `resources/rules.json`，发现新红线加一条即可，全团队同步。

## 四、清单不是万能的

清单只能检查「写下来的项」。它检查不了：

- 内容是否真实（夸大事实但没用极限词，清单抓不到）。
- 业务语境（同一句话在不同行业合规结论可能相反）。
- 细分行业的特殊监管要求（本工具只覆盖通用红线）。

所以清单的定位是「降低疏漏率」，不是「替代专业判断」。涉及医疗、金融、法律等高敏领域，清单跑完仍应走人工法务确认。
