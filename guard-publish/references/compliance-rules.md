# 合规红线与检测方法（guard-publish 引擎说明）

## 一、检测方式：纯静态正则 + 复合规则

guard-publish 引擎不依赖网络、不调用第三方服务，纯靠本地正则对文本文件做静态扫描。两种匹配模式：

### 1. 逐命中模式（内容规则）

对「表述本身即违规」的规则，引擎在文件里逐处匹配：

- `PUB-SUPERLATIVE`（高）：广告法禁止的绝对化用语——最好/最佳/国家级/世界级/顶级/全网最低/绝对/唯一指定。
- `PUB-MEDICAL-CLAIM`（极端）：疗效与安全承诺——根治/包治/无副作用/立竿见影/保证治愈。
- `PUB-INVEST-CLAIM`（极端）：收益承诺——保本/稳赚/零风险/保证收益/翻倍/躺赚。
- `PUB-PII-RAW`（极端）：未脱敏强个人信息——18 位身份证号字面、11 位手机号字面。
- `PUB-SECRET-HARDCODE`（极端）：明文密钥/凭据赋值。
- `PUB-INTERNAL-ADDR`（高）：内网地址、办公网、跳板机、堡垒机、预发布环境等运维入口。
- `PUB-DEBUG-LEFTOVER`（中）：调试开关仍开、测试账号、假数据残留。

每处命中带上下文窗口做白名单过滤（`dummy`/`test`/`sample`/`示例`/`虚构`/`仅为演示` 等语境放过），避免把练习文案误判为真实违规。

### 2. 文件级复合模式（缺失类规则）

对「有内容但缺配套声明」这类规则，引擎用 `req_regex`（必须出现该类内容）+ `absent_patterns`（不能出现该有的声明）做文件级单次判定：

- `PUB-NO-META`（中）：文件是产品/项目介绍类，却通篇无版本号、更新日志、授权任一项。
- `PUB-NO-DISCLAIMER`（高）：内容涉及医疗/金融/投资/税务等敏感领域，却无免责声明或风险提示。
- `PUB-NO-SOURCE`（中）：出现「据统计/占比 X%」这类量化断言，却未标注数据来源。
- `PUB-NO-PRIVACY-POLICY`（高）：涉及手机号/邮箱/注册登录等个人信息收集，却无隐私政策或授权说明。

复合规则避免「内容有了、声明也顺手写了」被误报，只在「内容有、声明无」时才提示。

注：缺失类规则不受示例/虚构白名单影响——因为「缺」本身就是缺口，练习文案也该养成写声明的习惯。

## 二、量化模型：发布合规指数

命中按严重度累加权重，封顶 100：

| 严重度 | 权重 |
|--------|------|
| 极端 | 100 |
| 高 | 40 |
| 中 | 12 |
| 低 | 3 |

**判定取严重度优先级链，不取平均**：只要有一条极端即判极端，有一条高且无极端即判高，如此类推。这样不会被一堆低危稀释掉真正高危的那一条——一条明文密钥就够判极端。

## 三、可整改性维度（本包原创量化点）

每条命中标明「可整改 / 不可整改」，区分的是**发布这个动作带来的不可逆程度**：

- **可整改**：发布前补上或删掉就能解决——极限词（删）、疗效与收益承诺（删）、缺免责声明（补）、缺隐私政策（补）、缺版本号（补）、调试残留（清）。
- **不可整改**：一旦发布即不可逆，只能轮换或已扩散收回不了——未脱敏个人信息（公开即被抓取扩散）、明文密钥（只能轮换，不能收回）、内网地址暴露（拓扑已公开）。

这个维度直接回答发布人最关心的问题：**「现在改还来不来得及？」** 报告里「可整改 X 处 / 不可整改 Y 处」是引擎按规则性质实算的，不是套话。

## 四、安全控制价值量化

把「没发生的发布事故」折算成可感知数字：按判定等级估算避免的发布后整改与召回工时——极端 8h / 高 4h / 中 1h / 低 0h。这是把合规成本语言化，让「发布前多跑一次检查」的投入有依据。

## 五、诚实边界（必须写明）

1. 只在静态内容层面检测，不实际拦发布、不修改内容。
2. 对内容是否真的发布、发到哪个平台、覆盖多少受众无感知。
3. 正则启发式，漏报与误报并存：换个说法表述同一承诺会漏；个别普通用词（如「绝对」在数学语境）会被误报。
4. 不可整改是「一旦发布就不可逆」的预警，不等于「已经发生泄露」。
5. 不替代法务合规审查与监管部门认定；地域与行业口径存在差异，规则只覆盖通用红线。
