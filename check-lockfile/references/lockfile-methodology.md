# 依赖锁定完整性护栏 方法论（check-lockfile）

本文件说明 check-lockfile 能判定什么、不能判定什么，以及各类规则背后的取舍。

## 一、能确定性判定的（本包范围）

1. 浮动版本未真锁：锁文件仍含 ^ ~ >= * x 等浮动范围，依赖可能随源漂移，定为中级。
2. 缺完整性哈希：依赖条目（resolved/url/name/version）存在却无 integrity/sha512/sha256/sha1/--hash，无法校验被篡改，定为中级。
3. 明文 http 源：锁文件从明文 http 源拉取依赖，传输可被中间人篡改注入恶意包，定为高级。
4. 未解析标记：锁文件含 unresolved/extraneous/missing dependency/not installed，依赖树不完整，定为中级。
5. 已启用依赖锁定：命中 lockfile/依赖锁/完整性校验/dependency lock，定为安全变体（仅鼓励信号，不计入发现项）。

## 二、不能判定、也不假装能判定的

1. 依赖版本本身有已知漏洞：本包不连漏洞库，不读 CVE/GHSA，会漏报「锁了但版本有洞」这类需要情报的缺陷。那是专业依赖审计器或 guard 深度版的活。
2. 依赖树真实拓扑与传递依赖冲突：本包只看单文件静态文本，不解析真实安装后的依赖图。
3. 锁文件「是否被提交到仓库 / 是否与源码版本一致」：那是流程与一致性检查，超出静态快检。

## 三、严重度设定

- 高：明文 http 源（LOCK-HTTP-SOURCE）。传输可被中间人篡改，是供应链投毒高危入口。
- 中：浮动版本、缺完整性哈希、未解析标记。这三类都让依赖锁定「看似锁了实则没锁死 / 锁不干净」，故定为中级并建议修复。
- 安全变体：已启用依赖锁定与完整性校验，仅鼓励信号，不计入发现项、不影响判定。

## 四、为什么用「模式匹配」而非实时执行/渲染

实时依赖解析需要连注册表或采样安装、慢、难进 CI、结果不稳定。本包只用不需要语义理解的确定性模式，因此可重跑、可留证据、可进 CI，专门拦住「浮动版本 / 缺哈希 / 明文源 / 未解析」这类一眼就能揪的锁定缺口。

## 五、如何扩展规则库

直接编辑 resources/rules.json，追加 {"id": "...", "layer": "...", "kind": "regex", ...} 即可，引擎在每次扫描时实时加载，无需改代码。
