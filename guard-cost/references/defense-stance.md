# 设计立场：为什么「看清账单后果再决定」，而不是「硬禁止」

## 1. 硬禁止会逼出绕过

和 guard 系列其他成员一样，本包最大的诱惑是把「禁止」当终点：一旦说「这个循环不能调 API」「这个模型太贵不能用」，真实世界里的开发者会立刻找到绕过——把调用藏进更隐蔽的地方、绕过检查脚本、或者在别的分支里偷偷调。结果比我不在场更糟：至少我在场时，这段代码还被「看见」过一次。

所以本包从一开始就是——**不硬禁止，只让你看清账单后果再决定**。

## 2. 这个立场落地成什么

- `scan`：扫描代码里付费 API 调用的成本雷区，给出严重度、可规避性、花费暴露指数；判定高/极端时退出码 4（已拦截），但「拦截」是信息层面的——提示你「先加护栏再上线」，不替代你的决策。
- `cap`：对 `model:次数xtoken` 简写或具体目录做花费投影，按参考单价算出「这笔会花多少」，干跑、不拦请求。
- `ledger`：把多次「拦下的先兆」聚合成价值账本，让成本防护的价值可见。

## 3. 诚实边界

- 我**不**实际拦截任何请求、不代你设预算。决策权始终在人。
- 我**不**感知运行时动态调用频次；只在被扫描的代码文本里看得到模式。
- 我**不**保证 100% 拦住所有超支。熔断/限流/预算也只是多层防御中的一层。
- 单价**仅**为参考估算，真实花费以服务商账单为准。

## 4. 误报会杀死产品

正因为不硬禁止，误报代价极高：如果把「正常的 for 循环」「常规带预算的调用」也报成高危，用户很快学会忽略我——一旦学会忽略，真正的 `while True` 调 API 也被一起忽略。所以规则设计上：复合规则要求「文件确实调了付费 API」才提示；缺预算/限速/熔断只报中危（鼓励补齐，而非阻断）；安全变体（预算常量/熔断装饰器/限速中间件）只作鼓励信号、不当命中。宁可在边界上保守，也不制造狼来了。
