# 把花费当受控变量：控制论视角与价值量化

## 1. 花费是一个该被「控制」的系统

控制论（Cybernetics）里，一个能稳定运行的系统必须有**设定点（预算）、执行器（熔断/限流）、反馈（计量）** 三个要素。把付费 API 的花费套进去：

- 设定点 = 你愿意为这个功能花的上限（MAX_COST / 预算常量）。
- 执行器 = 达到上限就停的熔断 / 限流逻辑。
- 反馈 = 实时计量花了多少、还剩多少。

如果一个系统**没有反馈回路**，它的输出必然发散——这正是「无计量、无上限的 API 调用」的真实写照：你以为在跑一个小功能，实际上在跑一个没有刹车的花钱机器。

## 2. 本包如何给这个系统「前馈预警」

真正运行时的事后计量（账单）是反馈，但那是**事后**的，钱已经花了。本包的「花费暴露指数」是个**前馈（feed-forward）预警**：在代码上线之前，先扫一遍它有没有刹车，估算一旦失控会炸多大（指数 0-100）。相当于在车子冲下悬崖前，先告诉你刹车片是空的。

## 3. 安全控制价值量化：把「没发生的超支」折算成数字

拦下一笔无护栏的付费调用后，它的价值怎么体现？不是省了多少钱（那要等真烧起来才知道），而是省了多少**人力响应成本**：

- 极端：约 8 小时（账单对账、定位超支点、止损、安抚业务方）。
- 高：约 4 小时。
- 中：约 1 小时。
- 低：0 小时。

这是 guard 系列统一打法（安全控制价值量化）在成本域的落地：把「没发生的灾难」变成可感知的人力工时，让防护价值可见。数字用于感知，不用于精确计费——真实花费永远以服务商账单为准。
